# 历史数据夹具草案

`history.json` 是本题原创的语义输入，不是统计答案。它描述2026-09-25至2026-10-16（含首尾）的5个习惯、89条记录及21个未记录单元。日期按UTC日历日定义；正式环境必须核对设备时区和当天日期后再使用，不能因运行日期变化而静默移动数据。

## 身份与数据

`id`是稳定的习惯身份，`name`只是显示名称。两个Read分别是二值阅读打卡和按分钟计量的数值习惯。Training的频率为每7天3次；Coffee的目标是每天至多2杯；Practice初始归档，但有历史记录。

记录由`habit_id`和`date`共同定位。`state=yes/no/skip`分别表示二值完成、明确未完成和跳过；数值记录使用`state=value`及精确十进制字符串`value`。不存在对应记录才表示未记录，不能补成实际0。`notes`必须随对应日期和习惯保存，不能因同名而串到另一条习惯。

此JSON是公开的初始状态说明，不强制App内部数据库格式。候选App的初始化接入方式与导出格式尚待冻结；当前不能假定原版可直接导入此JSON，也不能要求模型猜测私有SQLite结构。

## 组合操作

1. 分别打开两条Read，检查2026-09-28：二值为明确未完成，分钟数为15.50。只把分钟数改为40.00，二值历史保持不变。
2. 在2026-09-27的分钟习惯补记0.00。该日期由未记录变为实际0，记录总数增加1；再次改为12.00不能再增加记录。
3. 把2026-09-29的Training从跳过改为完成，检查当天、跨月后日期、首页与统计页的联动。派生数值须按后续冻结的完整算法判断，不能仅检查按钮颜色。
4. 将Coffee的2026-09-28从3.50改为1.50；至少与至多两种目标不能共用相反的达标判定。
5. 改变分钟习惯的目标，随后查看已有日期；目标变更的追溯规则尚待原版核验，冻结前不得作为隐含判分条件。
6. 恢复归档的Practice，再次归档，历史记录及备注应保留。修改排序后再编辑两条Read，仍按身份定位。
7. 保存、终止进程、重开，导出历史，按身份与日期逐条核对；之后验证备份恢复。正式导出与恢复契约仍待补齐。

此数据覆盖跨月但不覆盖跨年；跨年、闰日及非UTC时区将另设夹具。统计公式、连续记录和图表聚合尚未完整冻结，本输入不能单独充当完整Golden或可正式作答题包。
